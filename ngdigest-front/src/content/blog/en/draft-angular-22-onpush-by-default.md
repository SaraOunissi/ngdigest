In interviews, I have been asked about change detection almost every single time. The wording barely varies: "tell me about change detection, and about `OnPush`". And for years there was one good answer, the one everybody recited: "by default Angular checks the whole tree on every event, and `OnPush` is an optimisation you switch on for critical components". Since **3 June 2026**, that answer is wrong. Not imprecise: wrong. The default has swapped sides.

## What Actually Changed

Angular **22.0** shipped on **3 June 2026**. Three things moved at once on change detection.

1. **`OnPush` became the default strategy.** A component that declares no `changeDetection` is now `OnPush`. The API docs say it in plain text: *OnPush is enabled by default*.
2. **The old `Default` was renamed `Eager`.** The behaviour did not move an inch — check the whole subtree on every pass — but the name finally describes what the strategy does, instead of describing its position in a list. `Default` had already been deprecated in **21.2**.
3. **`Default` survives, on borrowed time.** It is still in the enum, marked `@deprecated`, strictly equivalent to `Eager`, and announced as due to be removed.

> The word "Default" no longer means anything: it now names the strategy that is precisely no longer the default.

:::warn A mistake already going around
No, `ChangeDetectionStrategy` did **not** turn into a union of string literals. As of 2 September 2026, the official API reference still documents it as an **`enum`**, exposing `OnPush`, `Eager` and `Default` (deprecated). If you read somewhere that the type changed nature, that source did not open the page.
:::

The useful mental model fits in two lines. **`Eager`**: the component is checked as soon as the detection pass reaches it, full stop. **`OnPush`**: it is checked only when one of four things happens — an `input()` receives a **new reference**, an event originates from the component itself, a **signal read in the template** changes, or someone explicitly calls `markForCheck()`.

## What `ng update` Really Does — and the Trap That Follows

This is the point that 90% of v22 articles cover in a single bullet, and it is the only one that matters when you land on an existing codebase.

The `ng update` migration **writes** `changeDetection: ChangeDetectionStrategy.Eager` onto every component that declared nothing. It also replaces `Default` with `Eager` in the decorators that mentioned it, and it keeps `OnPush` where it was already written (now redundant, but harmless).

The consequence is mechanical: **your migration breaks nothing, and that is exactly the problem.**

:::keyfigures What your codebase looks like after `ng update`
- bad | 100% | of existing components explicitly tagged `Eager`
- good | 0 | regressions at upgrade time
- neutral | 1 | place where the new default applies: components you create afterwards
:::

You come out of the migration with a codebase entirely frozen in the old mode, one extra annotation per file, and zero performance gain. The new default only applies to components born after the migration. And because nothing breaks, **nobody ever goes back over it**. That is the definition of silent debt: it is written down, it is visible in the diff, and it will never hurt enough to get prioritised.

So the real story of v22 is not the migration. It is the aftermath.

## The De-`Eager`-ing Checklist

A big bang — "let's strip every `Eager` at once" — is the best way to spend a week hunting components that stopped refreshing. The right granularity is the feature module, not the repo.

1. **Count your debt.** A `grep -rc "ChangeDetectionStrategy.Eager" src/` gives you the exact number to put on a slide. It is a metric that goes down, so it is a metric you can steer.
2. **Start with the leaves.** Presentational components that only receive `input()`s and hold no internal state move to `OnPush` without discussion. That is 60 to 70% of the volume in a well-split app, at near-zero risk.
3. **Then take the containers, one at a time.** They carry the subscriptions, the mutations and the third-party callbacks — that is where the three traps in the next section hide.
4. **Keep an explicit list of the `Eager` you chose to keep.** A component that stays `Eager` with a one-line comment explaining why is an architecture decision. The same component with no comment is an oversight. Twelve months later, nobody can tell the difference.

## The 3 Traps of the OnPush Component That "Doesn't Render"

They are always the same, and they are about to reappear in bulk now that the default has flipped.

1. **Mutating an object instead of passing a new reference.** `this.user.name = 'X'` triggers nothing: the `input()` reference did not change. You need `this.user = { ...this.user, name: 'X' }` — or better, stop passing mutable objects and pass signals.
2. **The hand-rolled RxJS subscription.** A `subscribe()` that writes into a class property notifies nobody. Either go through the `async` pipe in the template, or call `markForCheck()` inside the `subscribe`, or — the signal-first cure — convert the stream with `toSignal()` and read it in the template.
3. **The callback living outside Angular's cycle.** `setTimeout`, a third-party library listener, a map or charting SDK calling you back from its own world. State changes, Angular knows nothing about it. Same cure: write into a **signal** rather than a property, and the problem dissolves.

The thread running through all three: **`OnPush` does not punish performance, it punishes implicit state.** Every trap is a place where code changed data without telling anyone. The signal-first shift and the `OnPush` shift are the same shift seen from two sides.

## Your Interview Answer Is Out of Date — Here Is the New One

If you are interviewing for Angular roles this autumn, this is the highest-return update you can make, because the question lands almost every time and nearly every candidate will recite the old version.

**What you should stop saying**: "by default Angular checks everything, and `OnPush` is an optimisation you switch on".

**What to say instead**: since Angular 22, `OnPush` **is** the default; the old `Default` is called `Eager`; and on a migrated codebase everything pre-existing was explicitly tagged `Eager` by `ng update`, so in practice the new default only affects new code.

And the interesting question inverts. It is no longer "why move to `OnPush`?" — the answer became "nothing to do, it is the default". It is: **"where did you have to keep `Eager`, and why?"** Answering that one requires actually having been through a migration, and it shows within thirty seconds.

## The Client Angle: A Billable Work Package, Not a Refactor Line

On a client project, "we're going to move components to OnPush" does not sell: it sounds like developer comfort. Here is how I frame it instead.

A client on v20 or v21 will meet this shift at their next version bump, whether they like it or not. So you can arrive with a scoped, quotable package: the audit of how many components are affected, the technical migration, then **the de-`Eager`-ing pass, module by module**, with a measurable exit criterion (the count of remaining `Eager`, plus the documented list of exceptions). That is an identified work package with a start, an end and a number — not a request for free time to "improve the code".

The benefit pitches without jargon: less wasted work on every user interaction, more predictable rendering, and a codebase moving toward the model Angular is pushing anyway. For the wider market context — what clients are actually asking for on the front end right now — I broke the numbers down in [my article on the 2026 frontend / fullstack market](/en/blog/angular-frontend-fullstack-market-2026).

## Status as of 2 September 2026

Dated box, to re-check before any migration decision:

- **Version concerned**: Angular **22.0**, released **3 June 2026**. The API docs consulted were served by a **v22.1.4** build.
- **Exact naming**: `ChangeDetectionStrategy` is still an **`enum`**, with `OnPush`, `Eager`, and `Default` marked `@deprecated` ("Use `Eager` instead", due to be removed).
- **Automatic migration**: yes, included in `ng update` — it adds `ChangeDetectionStrategy.Eager` to components with no declared strategy.
- **`Default`**: deprecated since **21.2**, still present in v22 as an alias of `Eager`.

## What to Take Away

v22 did not add a performance option: it moved the default, and renamed the old default so it would stop lying about what it does. On an existing codebase, the real work starts **after** `ng update`, because the migration froze everything in the old mode without breaking anything — and therefore without flagging anything. And if you are interviewing, there is one sentence to unlearn before you go back into a process.
